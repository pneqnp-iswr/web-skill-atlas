# EF Core and migrations in QRAFIG

Stack: EF Core 10 with `Npgsql.EntityFrameworkCore.PostgreSQL`, against PostgreSQL 18. Versions live
in `Directory.Packages.props` — read them there rather than assuming.

## Read first

- `backend/src/Qrafig.Infrastructure/Persistence/QrafigDbContext.cs` — every `DbSet`.
- The `*Configurations.cs` file for the module you are changing (one per area:
  `SalesConfigurations`, `FinanceConfigurations`, `InventoryConfigurations`, …).
- `docs/implementation-status.md` → `## Migration history`. Each entry says what the migration did,
  what index carries the design, and **how it was verified**. It is the best specification of the
  house style in the repository.
- ADR-0008 (row_version), ADR-0018 (real PostgreSQL in tests), ADR-0019 (no retrying execution
  strategy), ADR-0003 (UUIDv7), ADR-0004/0005 (money and quantity types).

## Conventions

| | |
| --- | --- |
| Mapping | Explicit `IEntityTypeConfiguration<T>` per entity. No convention-only mapping. |
| Naming | snake_case tables and columns; index names `ix_…`, unique `ux_…`. |
| Keys | `Guid.CreateVersion7()` in application code — no database `DEFAULT`, no `SERIAL`. |
| Money | `bigint` minor units, beside an ISO 4217 currency code. |
| Quantity | `numeric(18,3)`. |
| Time | `timestamptz` / `DateTimeOffset`, UTC. |
| Concurrency | `row_version` token where mutation races matter. |
| Execution strategy | **No `EnableRetryOnFailure`** on the shared context — it replays a whole migration batch after a transient fault and fails with "relation already exists" (ADR-0019). |

## Generating a migration

```bash
dotnet ef migrations add <Name> \
  --project backend/src/Qrafig.Infrastructure \
  --startup-project backend/src/Qrafig.Api \
  --output-dir Persistence/Migrations

dotnet ef database update \
  --project backend/src/Qrafig.Infrastructure \
  --startup-project backend/src/Qrafig.Api
```

Then, always:

```bash
dotnet ef migrations has-pending-model-changes \
  --project backend/src/Qrafig.Infrastructure \
  --startup-project backend/src/Qrafig.Api      # must report no changes
```

**Migrations are generated by the tooling and are append-only once accepted.** Never hand-write or
hand-edit `QrafigDbContextModelSnapshot.cs`; never edit an accepted migration. If a generated
migration is wrong, change the model and generate another — or, before it is accepted, remove it with
`dotnet ef migrations remove` and regenerate.

In Development the API applies pending migrations at startup; turn that off with
`Database__AutoMigrateOnStartup=false` when something else owns schema deployment.

## Make the database the enforcer

QRAFIG's strongest invariants are **partial unique indexes**, not code paths. Examples worth copying:

- `ux_finance_entries_opening_balance` on `finance_entries (money_account_id) WHERE kind = 'OpeningBalance'`
  — "once only" becomes the database's word.
- `ux_outbox_deliveries_succeeded` on `(outbox_message_id, handler) WHERE outcome = 'Succeeded'`
  — failed attempts stay in the log as many times as they happened; a success can exist once.
- `ux_money_accounts_store_default` on `(store_id) WHERE is_default_for_store` — two tills opening a
  shift at one instant collide on the index rather than leaving two competing accounts.
- `ux_inventory_counts_open_per_store` on `(store_id) WHERE status IN ('InProgress','PendingApproval')`.

A code check in front of an index is a **performance optimization**, never the guarantee. Pair every
new uniqueness rule with a named-constraint translation for the loser (see `qrafig-concurrency`).

Partial indexes also keep hot queries small: claims, sweeps and queues index only the minority state
(`WHERE status = 'Reserved'`, `WHERE next_attempt_at IS NOT NULL`, `WHERE status IN ('Pending','RetryScheduled')`).

**Watch the EF foreign-key index interaction.** EF can treat a partial index as covering a foreign
key and drop the unfiltered one another read still needs. `FinanceFunctionalAlpha` renames and keeps
the unfiltered index for exactly this reason — check `Down`/`Up` for an index you did not intend to lose.

## Delete behaviours are design, not defaults

Decide each one deliberately and say why in the migration-history entry:

- **Cascade** where the child is meaningless without the parent (a support grant with its organization).
- **Restrict** where the record must outlive the reference (a shift adjustment's employee; a stored
  object referenced by a product image — cascading would leave bytes in the bucket that nothing in
  the database remembers).
- **SetNull** where the record of the act must survive its subject (a platform audit entry's organization).

## Data migrations: refuse rather than repair

When existing rows may already be in a state the new rule forbids, the `Up` **checks before it changes
anything and refuses with a named remedy**. QRAFIG does this repeatedly, and the reasoning is the same
each time: which of two opening balances is real, or which of two unresolved stocktakes to close, is a
question about a business's books that nothing in the row can answer. A silent repair is QRAFIG
inventing a fact and hiding the invention behind a successful migration.

A repair is allowed only where the rows **prove** the correction — the purchase-return repair moves a
`Draft` to `Sent` only where a matching `inventory_movements` row proves the shipment happened, same
organization and same reference type, and leaves every ambiguous row exactly as found.

Write `Down` honestly: leave it empty where reversing would corrupt rows created since (and say so),
and note when a `Down` needs no guard because it can only ever relax.

## Verification

1. `dotnet build` — 0 warnings.
2. `dotnet ef migrations has-pending-model-changes` — no changes.
3. Migration applies to a **fresh** database (the integration suite does this at host start, so a
   fresh-database failure appears as a setup error).
4. Migration applies **in sequence onto a populated database of the previous phase**. This is the gate
   the suite does not give you. Seed rows that exercise the case, apply, then assert: the pre-existing
   rows survived with their row versions untouched, the new objects exist with their filters intact,
   and the new invariant is refused **by the index itself** with the service check out of the picture.
5. Backend integration suite green.
6. Add a `## Migration history` row saying what changed, which index carries the design, and how it
   was verified.

## Query behaviour

- Reads that do not need tracking use `AsNoTracking()`.
- Projections go to contracts; **EF entities never leave the Application layer**.
- Watch for N+1 in list endpoints — project in one query rather than iterating navigations.
- Cursor pagination needs its index from the start (ADR-0055, ADR-0075); adding it later is a
  migration on a table that has meanwhile grown.
- Check the generated SQL when a query is non-obvious; see `qrafig-postgres` for plans.

## Do not

- Do not hand-edit the model snapshot or an accepted migration.
- Do not add `EnableRetryOnFailure` to the shared context.
- Do not enforce a new uniqueness rule only in code.
- Do not silently repair ambiguous business data in an `Up`.
- Do not use `decimal`, `float` or `double` for money.
- Do not add a `DEFAULT` that generates a key.
- Do not claim a migration is verified against a populated database if you only ran it against an
  empty one.
