# QRAFIG — agent bootstrap

QRAFIG is a multi-tenant SaaS retail platform: an ASP.NET Core modular monolith on PostgreSQL,
and **QRAFIG Desktop**, one installed WPF `QRAFIG.exe` containing every workspace. Both live in
this repository. The public marketing site is a separate repository (`Site-QRAFIG`).

This file is the routing and bootstrap layer only. Detailed procedure lives in skills under
`.claude/skills/`, which load on demand. Do not move skill content here.

## 1. Source of truth, in order

`docs/api-roadmap.md` states this hierarchy and it is binding:

1. **Product Bible** (product intent). No file of that exact name is in the tree; the closest
   artifacts are `О ПРОЕКТЕ` (*QRAFIG Platform — Master Specification v0.1*) and
   `Каким Должен стать QRafig.md`. Treat a missing Bible as an open question, never as licence
   to invent product rules.
2. `docs/api-roadmap.md` — ordered backend/API plan. **A roadmap item is never evidence of delivery.**
3. `docs/architecture-decisions.md` — append-only ADRs. A later ADR supersedes an earlier one;
   history is never rewritten.
4. `docs/implementation-status.md` — **authoritative record of what is actually built, migrated
   and tested.** Its `## Session handoff` table is the freshest block in the repository and can be
   ahead of the file's own header. When they disagree, the handoff row wins.
5. `docs/client-save-policy.md` — client persistence behaviour for every client.

`README.md` documents the runnable commands and the operational contracts (errors, idempotency,
jobs, storage, outbox, POS authority, shift accounting, Desktop).

## 2. Before you change anything

Run `/qrafig-router` — or, equivalently, do what it says:

1. Read `docs/implementation-status.md` **`## Session handoff`** (near the top). It names the last
   completed task, the current failing command, and the next concrete task.
2. Establish whether the work you were asked for is inside a **closed claim**. A "Functional Alpha
   complete" claim must not be reopened without being told to.
3. Find the ADRs that govern the area: `grep -n '^## ADR-' docs/architecture-decisions.md`, then
   read the ones your change could contradict.
4. Read the implementation. **Never infer a module's behaviour from a directory name.**

## 3. Non-negotiables

| | |
| --- | --- |
| **Do not guess** | If the repository can answer it, read the repository. Ask the user only about genuine product decisions the code cannot settle. |
| **Money** | `bigint` minor units + ISO 4217 code. Never `float`, `double` or `decimal` for money. All combination goes through `MoneyArithmetic` (checked, refuses rather than wraps). **Amounts in different currencies are never added.** |
| **Immutability** | Completed sales and financial documents are append-only. Corrections are new records (reversal, return, adjustment, void beside the sale), never edits. |
| **Inventory** | Balance is derived from append-only movements. Stock is never overwritten. |
| **Tenancy** | Every organization-scoped operation resolves `OrganizationContext` through `OrganizationContextResolver`. Non-members get `404`, never `403`. |
| **POS authority** | *Current authority* (may this happen now?) is re-read from the database. *Historical attribution* (who was at the till?) is never used to refuse synchronized work. The two never collapse. |
| **Concurrency** | For every read-modify-write, answer "what happens if two legitimate clients do this at once?" — and prove the answer with a test using independent clients. |
| **Warnings** | `TreatWarningsAsErrors=true`. Fix the cause; never suppress. |
| **Migrations** | Generated by EF tooling only, append-only once accepted. Never hand-edit `QrafigDbContextModelSnapshot.cs`. |
| **Secrets** | Never committed. user-secrets locally, environment variables in containers. Never log a signed URL, token, PIN or credential. |
| **Desktop** | The client renders server decisions and makes none of its own. Hiding a control is a courtesy, never a boundary. |
| **Evidence** | "It compiles" is not completion. A Desktop workspace is not complete until the shipped `QRAFIG.exe` has been driven through it on Windows (ADR-0191). |

## 4. The verification gate

The four commands in `README.md` § Verification are the gate. Run **the four test projects
separately** — a whole-solution `dotnet test` starts ~50 containers at default parallelism and takes
the Docker daemon down mid-run, which looks like hundreds of code failures and is not.

```bash
dotnet restore --force-evaluate
dotnet build                                   # 0 warnings, 0 errors
dotnet test backend/tests/Qrafig.UnitTests
dotnet test backend/tests/Qrafig.IntegrationTests        # Docker
dotnet test desktop/tests/Qrafig.Desktop.Tests
dotnet test desktop/tests/Qrafig.Desktop.EndToEndTests   # Docker
dotnet ef migrations has-pending-model-changes \
  --project backend/src/Qrafig.Infrastructure \
  --startup-project backend/src/Qrafig.Api
dotnet list package --vulnerable --include-transitive
```

Read the **current** expected test counts from `docs/implementation-status.md`; do not trust a number
quoted anywhere else, including in a skill. `/qrafig-verification` holds the gate matrix that says
which gates a given change class must pass, and which of them a Linux container cannot run.

Never report a gate as passing that you did not run. Say plainly which ones you could not run and why.

## 6. When sources conflict

1. The user's explicit current task.
2. A current QRAFIG documented invariant (ADR / status ledger / roadmap contract).
3. The current implementation contract (what the code and its tests actually enforce).
4. A QRAFIG-specific skill.
5. An official framework skill or documentation.
6. Generic engineering advice.

A generic best practice never overrides a QRAFIG invariant. If a generic rule says "refuse work from
an inactive employee" and QRAFIG says a synchronized offline sale from a since-suspended cashier
still lands (ADR-0056, ADR-0126), **QRAFIG wins**. Say so rather than silently blending the two.

## 7. Autonomy

Understand → inspect → route → plan → implement → test → inspect the failure → fix → verify → report.
Do not open with a list of questions the repository can answer. Do not stop at a plan. Do not declare
completion without evidence.
